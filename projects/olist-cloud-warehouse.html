Data warehouse na nuvem (Olist)

Um data warehouse no BigQuery alimentado por dados que chegam todo dia, com modelos dbt incrementais, alertas de atraso, Terraform e CI sem chaves.

Decisão que apoia
Onde investir em logística, com números de um warehouse em que o time pode confiar e cujo custo é conhecido.
Quem usa
Analistas e gestores que consultam os marts; o time de dados que mantém a plataforma.
Quanto custa errar
Uma tabela que muda de formato ou um número errado chega ao painel; uma chave de nuvem vazada dá acesso a tudo.
Como gera valor
Os dados chegam todo dia e só o que mudou é reprocessado; toda mudança é testada em BigQuery antes de ir ao ar, sem chave guardada em lugar nenhum. O relatório de decisão mostra que a nota cai a cada dia de atraso até uns seis dias (de 4,03 para 1,81) e depois estabiliza: vale investir em evitar atrasos curtos, não em encurtar os longos.
Riscos e limites
O fluxo diário é uma reprodução de eventos reais, não um sistema ao vivo; correlação em dados observacionais.

Problema

Um data warehouse só merece confiança se as tabelas mantêm o formato, se toda mudança é testada antes de chegar ao analista, se ninguém guarda uma chave de nuvem que não expira e se alguém sabe quanto cada consulta custa.

Solução

Os dados do marketplace Olist no BigQuery (região de São Paulo), chegando como chegam em produção: um fluxo diário de mudanças, em que o pedido é comprado, enviado, entregue e avaliado em dias diferentes. As tabelas fato se atualizam de forma incremental, a atualização dos dados é monitorada e uma falha abre um alerta. Infraestrutura em Terraform, contratos dbt em todas as tabelas e GitHub Actions que entram no Google Cloud por Workload Identity Federation, como duas contas de serviço com o mínimo de permissão.

Como funciona

  • O histórico de 2016 a 2018 é reproduzido um dia por dia real; cada lote substitui a própria partição no raw, então rodar de novo ou recuperar dias perdidos dá o mesmo resultado.
  • As tabelas fato reconstroem só os meses de compra com algum pedido alterado e trocam essas partições com jobs de cópia, porque o sandbox não tem MERGE.
  • Todo pull request reproduz 31 dias em datasets descartáveis, faz o build incremental e o completo, e falha se os dois não tiverem as mesmas linhas.
  • A atualização dos dados é conferida depois de cada deploy e a cada seis horas; uma falha abre uma issue no GitHub, e um runbook diz o que fazer.
  • O Terraform cria os datasets, duas contas de serviço, a federação de identidade e um papel customizado com uma única permissão.

Resultados

Resultados medidos, do repositório
1 diade dados novos por dia real, carregado sem duplicar e recuperando dias perdidos
80%+menos bytes lidos numa pergunta de um mês na tabela fato particionada, medido a cada deploy
0chaves de conta de serviço: o CI usa tokens de uma hora vindos da identidade OIDC do GitHub

Limites

O fluxo diário reproduz eventos reais, não um sistema ao vivo, e os dados têm cerca de 100 mil pedidos. O sandbox do BigQuery não tem Cloud Storage, então o estado do Terraform fica no Cloud Shell e ele é aplicado à mão.

Stack

BigQuery, Terraform, dbt, Workload Identity Federation, GitHub Actions
