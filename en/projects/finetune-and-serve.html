Fine-tune and serve

A 0.5B model fine-tuned on a free CPU runner to tag financial facts in 10-K sentences, served with llama.cpp.

VM cost ($147.17/month) and measured capacity (4.2 million requests a month per VM) come from the project's benchmark; API prices are list prices. The APIs' accuracy on this task was not measured.

Problem

Structured extraction is usually done by prompting a large model, and every request pays for a long prompt on an API or on hardware big enough for the model. Whether a small model trained for the one job does better and costs less is a question of measurement.

Solution

LoRA fine-tuning of Qwen2.5-0.5B on sentences from 10-K notes tagged by auditors with XBRL concepts (FiNER-139), export to GGUF with 8-bit and 4-bit quantization, and serving with llama.cpp. It is compared with prompting the same model and a 3B model on quality, latency, throughput and cost.

How it works

  • Train, quantize, evaluate and benchmark in one GitHub Actions workflow on a 4-core CPU.
  • Loss and output logits only at the answer tokens, so a 152k-token vocabulary fits in memory.
  • Every model served by the same llama-server with the same JSON schema enforced by the grammar.
  • Cost from a VM the runner's size against API list prices with the measured prompt sizes.

Results

Measured results, from the repository
0.82fact F1 at 4 bits (398 MB), against 0.65 for Qwen2.5-3B with six examples (gain +0.16, 95% paired-bootstrap interval +0.10 to +0.23) and 0.19 before fine-tuning
3.7×the requests per second of the 3B model on the same CPU (1.60 against 0.43)
$35per million requests self-hosted at full load; Claude Haiku 5.5 at list price would cost $45 to $91

Limits

One training run, stopped by its time budget at 79% of an epoch; the APIs' accuracy on the task was not measured, only their price.

Stack

PyTorch, PEFT, llama.cpp, GitHub Actions
