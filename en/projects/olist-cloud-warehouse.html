Problem

A warehouse is trusted only if its tables keep their shape, every change is tested before it reaches analysts, nobody holds a long-lived cloud key, and someone knows what each query costs.

Solution

The Olist marketplace data in BigQuery (Sao Paulo region), arriving the way production data does: a daily change feed in which orders are bought, shipped, delivered and reviewed on different days. The fact tables update incrementally, freshness is monitored and failures open an alert. Infrastructure in Terraform, dbt contracts on every table, and GitHub Actions that authenticate through Workload Identity Federation as two least-privilege service accounts.

How it works

  • The 2016-2018 history is replayed one day per real day; each batch replaces its own raw partition, so reruns and catch-ups after an outage are idempotent.
  • The fact tables rebuild only the purchase months with a changed order and swap them in with copy jobs, since the sandbox has no MERGE.
  • Every pull request replays 31 days in throwaway datasets, builds incrementally and from scratch, and fails unless both hold the same rows.
  • Freshness is checked after every deploy and every six hours; a failure opens a GitHub issue, and a runbook says what to do.
  • Terraform creates the datasets, two service accounts, the federation trust and a one-permission custom role.

Limits

The change feed replays real events rather than a live system, and the data is about 100,000 orders. The BigQuery sandbox has no Cloud Storage, so Terraform state stays in Cloud Shell and is applied by hand.
