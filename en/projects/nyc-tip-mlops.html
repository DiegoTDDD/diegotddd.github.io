NYC tip MLOps

A monthly retrain on new real data, promotion by a statistical test, a model registry, an API and drift monitoring.

How it creates value
Every month a challenger trained on the newest month goes live only if it is shown to be better (95% interval above zero), the API computes features exactly as training does, and data drift is detected (unknown payments from 4% to 13%).
Risks and limits
The model itself is weak (AUC 0.625); the value is in the engineering around it.

Problem

A model is only useful in production if every step around it can be trusted: repeatable training, a rule for which version is live, features computed the same way in serving, and a signal when the data changes.

Solution

An MLOps system around a classifier that predicts, when a NYC taxi ride ends and before payment, whether the tip will be more than 20%: MLflow tracking and registry, a FastAPI service, Evidently drift reports, a Streamlit operations dashboard, and CI that runs the whole loop including Docker.

How it works

  • No label leakage: no payment field is used, only what is known when the ride ends, which caps the score honestly.
  • Every month CI finds the newest TLC month, trains a challenger and compares it with the champion on the same out-of-time month; it is promoted only if the paired-bootstrap interval of the gain is above zero.
  • A test checks that the API computes features exactly as training does.
